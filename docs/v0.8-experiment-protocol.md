# V0.8 Experiment Protocol — Candidate: Multi-Constraint Invoice Extraction

Status: PRE-REGISTERED (written before any comparative result for this workload).

## 1. Workload

Multi-constraint invoice line-item extraction. Each task is a short invoice-like
text; the model must return a JSON object with these fields (all required):

- `vendor` (string, exact)
- `invoice_number` (string, exact)
- `invoice_date` (YYYY-MM-DD)
- `due_date` (YYYY-MM-DD or "none")
- `currency` (ISO code)
- `total_amount` (string, two decimals, e.g. "1234.56")
- `line_items` (array of objects: {description, quantity, unit_price, amount})
- `tax_amount` (string, two decimals)

Success (oracle, deterministic): parsed JSON matches gold on every field, including
each line item's four sub-fields in order, and the cross-field invariant
`sum(line_items[].amount) + tax_amount == total_amount` (decimal, exact). Any
parse failure, missing/extra field, or invariant violation is a failure.

Rationale for selection (Phase 2 of Sprint 2):
- Candidate 1 (this one): cross-field consistency gives a deterministic,
  model-free validator; failure modes (dropped line item, wrong total, wrong tax)
  are detectable without a judge. This is the strongest candidate for a
  measurable capability difference.
- Candidate 2 (overlapping-category intent classification): needs a gold mapping
  and a model judge for borderline cases; deferred.
- Candidate 3 (noisy-document extraction): OCR noise is realistic but the noise
  generator itself becomes the experiment; deferred until candidate 1 is resolved.

Honesty label: synthetic evaluation set, not real customer traffic.

## 2. Splits

- `calibration`: 120 tasks (≥60 per capability class so the admission rule can fire).
- `pilot`: 10 tasks.
- `heldout`: 100 tasks (sealed; never read or tuned before the final run).

Seed: 20261027. Generator: `experiments/benchmark/tasks_v2.py` (to be added only
after this protocol is committed; not yet implemented).

## 3. Models

- Cheap: `gemini-3.5-flash-lite` (verified available 2026-10-27).
- Strong: `gemini-3.8-flash` (verified UNAVAILABLE on 2026-10-27: read timeout).
  No comparative run is authorized until availability is re-verified with a
  minimal smoke request on the day of the run. No silent substitution.

## 4. Strategies

1. `fixed_large` — always strong model (quality baseline).
2. `cost_aware_small` — always cheap model (cost baseline).
3. `crest_policy` — evidence-gated admission per capability class using the
   Wilson upper bound at 95% (one-sided), threshold 0.05 (primary).

Secondary (pre-registered sensitivity, reported separately, NOT the headline):
admission threshold 0.10, to quantify how much the threshold drives the result.
The headline criterion uses 0.05 only.

## 5. Output-quality metric

Task success = exact match on all fields plus the cross-field invariant.
Reported as success rate with Wilson 95% intervals.

## 6. Cost accounting

Provider-reported input/output tokens (cost_known flag). USD is an estimate under
the printed assumption table; no authoritative price is claimed. Stop the run if
any allowed response has cost_known=False or an unpriceable model.

## 7. Latency and failure metrics

Per-attempt latency (ms), attempt count (retries count toward the cap), provider
error codes, unknown-usage count, budget violations. Median and p95 latency
reported only when n ≥ 20 per strategy.

## 8. Budget cap

- Max request attempts: 80 (pilot stage); expansion requires explicit approval.
- USD cap: $0.10.
- Calibration: ≤ 240 attempts (120 tasks × 2 models? calibration uses the cheap
  model only for admission, so ≤ 120 attempts + retries).

## 9. Exclusion rules

- Tasks whose chosen model is unavailable are recorded as NOT_RUN with
  `status_reason=MODEL_UNAVAILABLE` and are NOT counted as successes or failures.
- Tasks that time out after the bounded retry limit are recorded as FAILED with
  the provider error; they count as failures in success-rate denominators.
- No held-out task may be read, scored, or used for routing before the final run.

## 10. Success criterion

CREST policy vs `fixed_large`, on the held-out set:

- ≥ 20% lower estimated token cost, AND
- ≤ 2 percentage-point lower task success rate, AND
- zero silent budget or retry violations, AND
- reproducible from the published seed/config.

Provisional engineering target, not a scientific guarantee.

## 11. Uncertainty reporting

Wilson 95% intervals on success rates; paired disagreement counts between
strategies; per-task failure categories (field-level). No general superiority
claim from a pilot.

## 12. Conditions that make the result inconclusive

- Strong model unavailable → no live comparative result (record as PARTIAL).
- Fewer than 52 calibration successes per class → admission cannot fire (report
  as a structural limitation, not a model result).
- Sample size < 100 held-out tasks → label preliminary.
- Provider usage missing → stop and report unknown cost.

## 13. Admission threshold investigation (mathematical)

The Wilson upper bound at 95% (one-sided) with zero observed failures reaches
0.05 only at n ≥ 52 (computed: n ≥ 0.95·z²/0.05, z=1.645, z²=2.706 → n≥51.4).
Therefore the calibration split must contain at least 52 (preferably 60+) tasks
per capability class. This protocol sets calibration to 120 total to satisfy that
with two classes. This is a property of the rule, not an empirical tuning.
