## 2. Audit of the seven questions

1. **Same tasks for all strategies?** YES. `_run_strategy` iterates the identical
   `pilot` list for every strategy (`experiments/benchmark/pilot.py`). Verified by
   inspecting `pilot_rows`: each strategy has the same 10 task_ids.

2. **Routing features exclude answers and evaluation labels?** YES. `derive_features`
   reads only `task.text`; `RoutingFeatures` has no gold/answer field (test
   `test_derive_features_does_not_read_gold_labels` enforces this). Calibration
   uses gold labels to score the cheap model and build the admission table — that
   is permitted (calibration labels are not held-out labels) and is documented.

3. **Failed requests and retries represented correctly?** YES. Rows carry
   `allowed`, `status_reason`, `attempts`, `cost_known`. Denied rows have
   `correct=None`. Retries count against the request cap via `BudgetGuard`.
   One gap found and fixed: `not_run` rows (model unavailable) were counted in a
   separate list and omitted from the per-strategy `tasks_total`/`tasks_not_run`
   summary. Fixed: `_summarize` now reports `tasks_total`, `tasks_attempted`,
   `tasks_not_run` per strategy (commit pending).

4. **Model unavailability distinguished from task failure?** YES after the fix.
   Rows with `status_reason == "MODEL_UNAVAILABLE"` and `not_run == True` are
   recorded separately and never counted as successes or failures of the task.

5. **Provider-reported usage distinguished from estimated cost?** YES.
   `cost_known` flag on every result; pricing labeled `ASSUMPTION-UNVERIFIED`;
   `actual_cost_available: False` in the artifact; USD figures prefixed as
   estimates. No authoritative price is claimed.

6. **Admission threshold calibrated from appropriate data?** NO — this is the
   key mathematical finding. The threshold is 0.05 on a one-sided 95% Wilson
   upper bound (`src/crest/policy.py::failure_upper_bound_at`). With zero observed
   failures in `n` calibration tasks, the upper bound is `z²/(n+z²)` (z=1.645),
   which reaches 0.05 only when `n ≥ 0.95·z²/0.05 ≈ 52`. The pilot had 22 and 8
   successes per class, so admission was impossible regardless of model quality.
   This is a property of the rule, not of the model. The previous report's
   "needs ~50+" estimate is confirmed exactly: **≥52 calibration successes per
   class are required before a single admission can occur at this threshold.**

7. **Reproducible without live API calls?** YES. Fake mode is deterministic
   (summary and rows identical across runs aside from timing; latency excluded
   from the reproducibility comparison). Live mode requires network and a
   healthy strong model.

## 5. Conclusion of the audit

The harness, invariants, and measurement pipeline are sound. The two blocking
issues are (a) strong-model unavailability and (b) an admission threshold that
cannot fire below ~52 calibration successes per class. Neither is a code defect;
both are experimental-design constraints that the next protocol must address.
