# V0.7 Benchmark Plan — "Support-Ticket Field Extraction"

Status: PRE-REGISTERED (written and committed before any comparative live result exists).

## Objective

Measure whether CREST-style evidence-gated model routing completes a defined
class of structured tasks with **lower actual token cost** than simpler
approaches at **comparable task success and reliability**, using the real
CREST inference runtime (`src/crest/inference.py`).

## Workload (synthetic, documented — NOT real customer traffic)

Support-ticket structured extraction: each task is a short ticket text; the
model must return a JSON object with exactly four fields:

- `category` ∈ {billing_refund, access_request, data_fix, report_bug, account_update, general_help}
- `urgency` ∈ {routine, urgent}
- `refund_requested` ∈ {yes, no}
- `due_date` ∈ {YYYY-MM-DD, or the literal string "none"}

Scoring (rule-based oracle, no model judge): a task attempt is **correct**
iff the parsed response JSON contains all four fields with values exactly
equal to the gold labels (string comparison after `strip()`). Any parse
failure, missing field, forbidden extra-key set difference is a failure.
This is exact-match scoring, deliberately conservative.

Dataset: deterministic generator (`experiments/benchmark/tasks.py`), seed
`20261025`. Split (fixed by task_id hashing; held-out is generated but must
not be read or scored before the final held-out run):

- `calibration` (120): available to CREST routing development/calibration (≥60 per
  capability class so the Wilson admission rule can fire at 0 observed failures).
- `pilot` (10): representative sample drawn from the same distribution,
  fixed membership in this file and the generated manifest.
- `heldout` (100): generated, never used for routing decisions or tuning.
  Tuning/examination of these examples before the final run is prohibited.

Honesty label: this is a **synthetic evaluation set**. It demonstrates the
mechanism and the measurement pipeline; it is not evidence about real user
workloads.

## Strategies (identical inputs, identical constraints)

1. `fixed_large` — always request the strong model. Baseline for quality.
2. `cost_aware_small` — always request the cheap model, no per-task judgment.
   Baseline for pure cost reduction.
3. `crest_policy` — evidence-gated admission: a task is routed to the cheap
   model only if the cheap model was **admitted for the task's capability
   class** by a calibration rule with a binomial failure upper bound
   (Wilson/CP-style upper bound as in `src/crest/policy.py`) below the
   success threshold at 95% confidence; otherwise the strong model is used.
   Routing inputs are task-text features only — **gold labels are never
   consulted for any routing decision**, calibration routes are scored only
   to build the admission table, and the calibration admission table is
   produced and published before any held-out attempt.

Shared constraints for all strategies: temperature 0, identical prompts,
identical `max_output_tokens`, identical per-request timeout, identical
validation and scoring, identical retry policy (`max_attempts=3`,
`retry_on_transient=True`, `retry_backoff_seconds=3.0`). Provider: Google
Gemini OpenAI-compatible endpoint (`generativelanguage.googleapis.com`),
same provider for every strategy. Cheap model: `gemini-3.5-flash-lite`.
Strong model: `gemini-3.8-flash` (included only while it responds healthily;
per-task 503 failures after the bounded-retry limit are recorded, never
silently retried beyond the limit, and never auto-switched to another model).

## Pre-registered success criterion (initial experiment)

CREST policy vs `fixed_large` baseline, on the held-out set:

- ≥ 20% lower actual token cost (provider-reported usage combined), **and**
- ≤ 2 percentage-point lower task success rate (must stay within), **and**
- zero silent budget or retry violations (all ledger-consistent), **and**
- results reproducible by re-running with the published seed/config.

This is a provisional engineering target for the first experiment, not a
scientific guarantee; sample size (100 held-out tasks) supports only a
pilot-scale comparison. Report exact uncertainty (Wilson intervals) either way.

## Measured quantities per attempt

Provider-reported input/output tokens (usage; `cost_known` flag when usage
is denied/missing), latency from the runtime, attempt count (retries count
against the request cap), final status, and oracle correctness. Cost:

- **actual cost** is only reported when the provider publishes authoritative
  prices for the exact model; otherwise usage is reported and USD cost is an
  **estimate** under the printed price assumptions below. Pricing
  assumptions are checked against the provider's published pricing page and
  recorded in the artifact.

## Operational budget guard (enforced before the first live call)

Printed before the run and enforced by the runner:

- model IDs and endpoint used;
- maximum possible requests (attempts incl. retries) for the stage;
- hard monetary cap in USD (finish-early if reached);
- strict stop if `cost_known == False` on any completed response (usage
  unknown ⇒ stop rather than continue with unpriced meters);
- request cap counts retries and failures (unused reservations are never
  reflected, matching the never-refund budget invariant).

Pilot stage: 10 tasks × up to 3 strategies (+30 cheap-model calibration
calls for the CREST admission table) ≤ 80 request-attempts, USD cap `$0.05`.
Expanding toward ~250 calls requires explicit user approval after the pilot.

## Fake-mode separation

`FakeModelAdapter`/deterministic fixtures power unit tests and regression
runs. Their outputs are labeled `mode: "fake"` in artifacts and are never
mixed with, or compared against, live artifacts (`mode: "live"`).
